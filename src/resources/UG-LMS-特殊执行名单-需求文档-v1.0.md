## 1. 背景与问题

贷中调额的现有流程是：**DE（风控决策引擎）每月全量跑批 → 风控依据跑批落库结果线下圈选用户 → 形成调额名单文件 → 交大数据执行调额**（落到 LMS → 核心 ECW 实际改额度）。

问题在于，调额策略对所有人一视同仁，但下面这几类人**不能被常规策略碰**：

- **Staff 组、白名单**：不能被降额（降自己人/白名单用户会引发投诉与合规问题），但提额合理；
- **风险触发组、人工降额名单**：不能被提额（已经因风险被人工压过额度，系统不能自动提回去）；
- **回捞组、激进提额组、降额实验组、模型切换实验组**：在实验期/回捞期内**完全不能被常规策略干扰**，否则组内样本被污染，实验结论不可信。

目前没有机制承载这件事：风控靠人工记着"这批人不要动"，一旦漏记或交接断层，就会误伤。

## 2. 目标与范围

**目标**：建一张"非常规组名单"，并在**每次调额执行前**按名单做门禁，实现三类差异化处理；常规用户不存表、默认走常规逻辑。

**In Scope（v1.0）**

- 名单表与维护后台（文件上传覆盖 / 单条新增 / 批次管理）
- LMS 调额执行前的名单校验（覆盖所有调额入口）
- 拦截留痕与对账

**Out of Scope（v1.0 明确不做）**

- ❌ **冷却期**：本期不做 cooldown，只要在名单内即生效
- ❌ 贷前、催收、短信触达等其他场景的名单复用
- ❌ 一人多标签（本期一人仅允许一个标签）

## 3. 术语与角色

| 术语 | 说明 |
| --- | --- |
| 非常规组名单 | 只存需要特殊处理的用户/账户，常规用户不入表 |
| 执行标签 | 决定调额时怎么处理的标签：不参与调额 / 仅参与提额 / 仅参与降额 |
| 标签层级 | `user`（绑客户，跨账户）/ `account`（绑账户） |
| 批次 | 一次名单导入产生的一批数据；同一时刻只有 1 个批次生效 |

| 角色 | 职责 |
| --- | --- |
| 风控 | 圈定名单、确定执行标签 |
| 运营/额度岗 | 在后台维护名单、上传/导入、查看拦截结果 |

## 4. 名单模型

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| third_customer_id | string | 是 | 用户唯一标识（用户级标签的绑定键） |
| overdraft_id | string | 账户级必填 | 账户唯一标识 |
| tag_level | string | 是 | `user` / `account` |
| pool_type | string | 是 | `no_adjust` / `increase_only` / `decrease_only` |
| detail_group | string | 否 | 明细组：Staff组 / 白名单 / 风险触发组 / 回捞组 … |
| source | string | 是 | `file` / `manual` / `rule` |
| batch_no | string | 是 | 所属批次 |
| operator | string | 是 | 操作人 |
| remark | string | 否 | 备注 |
| created_at / updated_at | timestamp | 是 | 时间戳 |

**三类执行标签**

| 执行标签 | 提额 | 降额 | 典型场景 |
| --- | --- | --- | --- |
| 不参与调额 `no_adjust` | ❌ | ❌ | Staff 以外的实验组、回捞组 |
| 仅参与提额 `increase_only` | ✅ | ❌ | Staff 组、白名单 |
| 仅参与降额 `decrease_only` | ❌ | ✅ | 风险触发组、人工降额名单 |
| 未命中 | ✅ | ✅ | 常规用户 |

## 5. 名单维护方式

### 5.1 文件上传（默认覆盖）

- 上传 Excel/CSV，**解析成功后生成新批次，新批次立即生效，上一生效批次自动标记为「已覆盖」**
- 上传前展示解析结果预览（解析条数 / 校验通过 / 重复或非法）
- **校验不通过则整批不导入**，不产生新批次
- 字段校验：`third_customer_id` 必填；`tag_level=account` 时 `overdraft_id` 必填；`pool_type` 必须在枚举内
- **一人一标签**：同一 `third_customer_id` 在本批次内或与现网数据冲突时报错，整批失败并给出重复明细

### 5.2 单条新增

- 表单录入一条，追加到当前生效批次
- 同样执行"一人一标签"与必填校验，冲突时给出明确提示（如：*该用户已有标签（仅参与提额），一人仅允许一个标签*）

### 5.3 批次管理

- 批次列表：批次号 / 来源 / 条数 / 状态 / 操作人 / 创建时间
- 批次状态：`生效中` / `已覆盖` / `已作废`
- 支持把历史批次**恢复为生效批次**
- 同一时刻仅一个批次生效

### 5.4 名单列表交互

- **分页**：显示总条数、每页条数（10 / 20 / 50 / 100）、页码、跳页；名单量级为几十万，分页为必需能力
- **查询**：按用户标识 / 账户标识检索，筛选后回到第 1 页
- **移除**：单条从当前名单移除
- 分页与查询由后端分页查询实现（不要把全量名单拉到前端）

## 6. 生效规则

- **在库即生效**：只要在生效批次内，立即参与调额校验；无冷却期、无生效延迟
- 退出名单：从名单中移除即恢复常规逻辑（本期不做自动到期，手工维护）

## 7. 执行时的匹配与拦截

### 7.1 校验位置（关键）

调额执行链路：**DE → LMS → ECW（核心额度系统）**

LMS 逐条调额的现有执行顺序（`QuotaImportProcessServiceImpl.processLimitUpdate`）：

```
① 读明细 → ② 冷却期校验 → ③ 比对目标额度 vs 当前额度 → 确定方向（提额/降额）
        → ④ 计算可用额度 → ⑤ 调用核心 ECW 改额度 → ⑥ 落额度历史与流水
```

**名单校验插入在 ③ 之后、⑤ 之前。** 原因：判断"只提不降 / 只降不提"必须先知道本次方向。

### 7.2 必须覆盖所有调额入口

- 校验放在**共用的执行方法**中，所有调额入口（DE 推批次、人工 Excel 批量导入等）都经过它，一次覆盖全部入口
- **不允许**只在某一个入口做校验

### 7.3 为什么不能只在导入批次时校验

**目标额度是导入时确定的，但当前额度是执行那一刻读取的**，中间用户额度可能已变化，方向会变。因此：

- **执行时校验是权威的**（必须做）
- 导入/生成批次时可做提前预筛（可选，用于减少无谓执行），但不能替代执行时校验

### 7.4 匹配规则

```
按 third_customer_id 匹配（tag_level = user）
    ↓ 未命中
按 overdraft_id 匹配（tag_level = account）
    ↓
命中 → 按 pool_type 决定放行/拦截；未命中 → 走常规逻辑
```

**拦截矩阵**

| 名单命中 | 本次方向=提额 | 本次方向=降额 | 处理 |
| --- | --- | --- | --- |
| 不参与调额 | ❌ 拦截 | ❌ 拦截 | 维持当前额度，不调核心 |
| 仅参与提额 | ✅ 放行 | ❌ 拦截 | 降额时维持当前额度 |
| 仅参与降额 | ❌ 拦截 | ✅ 放行 | 提额时维持当前额度 |
| 未命中 | ✅ 放行 | ✅ 放行 | 常规逻辑 |

## 8. 异常与兜底

| 场景 | 处理 |
| --- | --- |
| 名单查询报错 / 超时 | **整批终止**，不做静默放行；记录失败原因并告警，人工介入后重跑 |
| 名单为空 | 视为未命中，全部走常规逻辑（需在下发前确认名单已上传） |
| 用户不在名单 | 走常规逻辑 |

> 说明：选择"整批终止"是因为漏拦（该拦没拦）会放大风险敞口与实验污染；常规逻辑在名单可用后重跑即可补上。

## 9. 留痕与可追溯

- 被拦截的记录：写入执行明细的处理状态**「跳过」**，并写明**具体原因**：
  - `命中非常规组-不参与调额`
  - `命中非常规组-仅参与提额`
  - `命中非常规组-仅参与降额`
- 禁止只写笼统的「跳过」
- 每条拦截记录保留：用户/账户标识、本次方向、命中的执行标签、命中的明细组、所用批次号
- **批次快照**：一次调额执行使用同一版名单（记录批次号），避免执行途中名单变更导致前后口径不一致
- 对账口径：风控圈选 N 条 → 实际执行 M 条 → 拦截 N−M 条，可按原因/标签/明细组下钻

## 10. 性能与容量

- 名单规模预计**几十万条**
- ❌ 禁止在逐条执行循环中逐条查库
- ✅ 推荐：批次开始时**一次性加载名单到内存**（或与明细表做 join 合并），循环内做本地匹配
- 需要研发给出：一次调额批次规模 × 名单规模下的执行耗时评估

## 11. 关键约束

1. **一人一标签**：同一 `third_customer_id` 仅允许一条有效记录；导入时校验唯一性，重复整批失败
2. **用户级优先**：同一用户先匹配 `user` 级标签；未命中才匹配 `account` 级
3. **同一时刻仅一个生效批次**
4. 名单表只存非常规用户，常规用户不入表

## 12. 验收要点

1. 未命中名单的用户，提额/降额均按常规执行，行为与改造前一致
2. 命中「不参与调额」的用户：不论方向，均标记跳过、原因 `命中非常规组-不参与调额`，且**不调用核心接口**
3. 命中「仅参与提额」的用户：本次为提额时正常执行；本次为降额时标记跳过、原因 `命中非常规组-仅参与提额`，额度维持不变
4. 命中「仅参与降额」的用户：本次为降额时正常执行；本次为提额时标记跳过、原因 `命中非常规组-仅参与降额`
5. **所有调额入口**（DE 推批次、人工批量导入）都触发名单校验
6. 模拟名单查询异常 → **整批终止**且不产生任何额度变更，有明确错误提示
7. 上传文件包含重复 `third_customer_id` → 整批导入失败并给出重复明细
8. 上传成功后：新批次生效，上一批次状态变为「已覆盖」，名单条数与文件一致
9. 单条新增已存在标签的用户 → 拦截并提示"一人仅允许一个标签"
10. 拦截记录可按原因、执行标签、明细组查询与导出，用于与风控圈选名单对账
