## 0. 本版变更摘要（v1.0 → v1.1）

1. **单 ID 互斥**：用户级记录只允许携带 `third_customer_id`、账户级记录只允许携带 `overdraft_id`，两列均不允许出现对方层级的 ID；
2. **导入语义**：由「全量覆盖」改为**增量合并**——同键（同层级同 ID）以新文件为准覆盖，其余记录（含手工维护）全部保留；任一行校验不通过 → 本次整批放弃；上传预览改为「解析 / 新增 / 覆盖 / 非法」；
3. **新增有效期**：`effective_start` / `effective_end` 全必填，时间格式固定 `YYYY-MM-DD HH:mm:ss`；开始时间不得早于当前（opco 本地时间）；到期自动失效；
4. **匹配优先级修正**：执行端由「先用户级后账户级」改为 **「先账户级（overdraft_id）后用户级（third_customer_id）」**——账户级池全部是「不参与调额」（全锁、最严格），先命中可同时保证实验样本纯净与用户级保护不被稀释（详见 7.4；此为对 v1.0 的**有意修正**）；
5. **一人一标签放宽**：由「全名单内一人仅一条」改为**「同键唯一 + 跨层级共存」**——同一个人的用户级记录与其各账户的账户级记录可并存，执行端按优先级裁决；
6. **批次模型**：批次由「名单版本」改为**「一次导入的变更记录」**；状态机为 **处理中 / 已生效 / 处理失败**；操作列仅「详情」；「生效批次」「恢复为生效」概念取消；
7. **维护能力**：新增 **单条删除**（不可恢复）与 **停用 / 启用（不删除）**；记录状态派生展示（未生效 / 生效中 / 已失效 / 已停用）；
8. **筛选与命名**：名单筛选扩展为 9 项（third_customer_id、overdraft_id、生效时间范围、失效时间范围、明细组、标签层级、执行标签、来源、状态）；「用户标识 / 账户标识」统一更名为 `third_customer_id` / `overdraft_id`。

> 变更依据：2026-10-15 用户调研（14 条需求更正）与 2026-10-16 评审讨论（增量合并、有效期、odid → tcid 优先级）。

## 1. 背景与问题

贷中调额的现有流程是：**DE（风控决策引擎）每月全量跑批 → 风控依据跑批落库结果线下圈选用户 → 形成调额名单文件 → 交大数据执行调额**（落到 LMS → 核心 ECW 实际改额度）。

问题在于，调额策略对所有人一视同仁，但下面这几类人**不能被常规策略碰**：

- **Staff 组、白名单**：不能被降额（降自己人/白名单用户会引发投诉与合规问题），但提额合理；
- **风险触发组、人工降额名单**：不能被提额（已经因风险被人工压过额度，系统不能自动提回去）；
- **回捞组、激进提额组、降额实验组、模型切换实验组**：在实验期/回捞期内**完全不能被常规策略干扰**，否则组内样本被污染，实验结论不可信。

目前没有机制承载这件事：风控靠人工记着"这批人不要动"，一旦漏记或交接断层，就会误伤。

## 2. 目标与范围

**目标**：建一张"非常规组名单"，并在**每次调额执行前**按名单做门禁，实现三类差异化处理；常规用户不存表、默认走常规逻辑。

**In Scope（v1.1）**

- 名单表与维护后台（增量导入 / 单条新增 / 单条删除 / 停用·启用 / 批次管理）
- 名单有效期（生效 / 失效时间）
- LMS 调额执行前的名单校验（覆盖所有调额入口；命中优先级 odid → tcid）
- 拦截留痕与对账

**Out of Scope（v1.1 明确不做）**

- ❌ **冷却期**：不做 cooldown，仅按有效期窗口生效
- ❌ 贷前、催收、短信触达等其他场景的名单复用
- ❌ 同层级内的多记录与更复杂的优先级裁决（本期为「同键唯一 + 固定 odid → tcid 优先级」）

## 3. 术语与角色

| 术语 | 说明 |
| --- | --- |
| 非常规组名单 | 只存需要特殊处理的用户/账户，常规用户不入表 |
| 执行标签 | 决定调额时怎么处理的标签：不参与调额 / 仅参与提额 / 仅参与降额 |
| 标签层级 | `user`（绑客户，跨账户）/ `account`（绑账户） |
| 单 ID 互斥 | 用户级记录只带 `third_customer_id`、账户级记录只带 `overdraft_id`；不允许出现对方层级的 ID |
| 同键 | 同一层级内相同的 ID（用户级看 `third_customer_id`、账户级看 `overdraft_id`） |
| 增量合并 | 导入时「同键用新值覆盖、其余保留」的合并方式 |
| 批次 | 一次导入的变更记录（**不是**名单版本）；状态：处理中 / 已生效 / 处理失败 |
| 有效期 | 记录在 [生效时间, 失效时间) 内参与调额匹配；到期自动失效 |
| 命中优先级 | 执行端先按 `overdraft_id` 命中账户级；未命中再按 `third_customer_id` 命中用户级 |

| 角色 | 职责 |
| --- | --- |
| 风控 | 圈定名单、确定执行标签 |
| 运营/额度岗 | 在后台维护名单、上传/导入、停用/删除、查看拦截结果 |

## 4. 名单模型

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| third_customer_id | string | 用户级必填 | 用户唯一标识；**用户级记录仅允许携带此 ID** |
| overdraft_id | string | 账户级必填 | 账户唯一标识；**账户级记录仅允许携带此 ID** |
| tag_level | string | 是 | `user` / `account` |
| pool_type | string | 是 | `no_adjust` / `increase_only` / `decrease_only` |
| detail_group | string | 否 | 明细组，8 个预设组之一：回捞组 / 激进提额组 / 降额实验组 / 模型切换实验组 / Staff组 / 白名单组 / 风险触发组 / 人工降额名单组 |
| effective_start | datetime | 是 | 生效时间；不得早于提交时的当前时间（opco 本地时间） |
| effective_end | datetime | 是 | 失效时间；必须晚于生效时间；不设上限 |
| source | string | 是 | `file`（文件上传）/ `manual`（手工维护） |
| batch_no | string | 是 | 最近一次更新该记录的导入批次（手工记录沿用其所在上下文） |
| operator | string | 是 | 操作人 |
| remark | string | 否 | 备注 |
| created_at / updated_at | timestamp | 是 | 时间戳 |

**存储约束**

- **单 ID 互斥**：用户级行 `overdraft_id` 必须为空；账户级行 `third_customer_id` 必须为空；
- **同键唯一**：同一层级内同一 ID 仅允许一条记录；再次导入 = 用新值覆盖（增量合并）；单条新增同键已存在 → 拦截提示；
- **跨层级共存**：同一个人的用户级记录与其各账户的账户级记录允许并存（执行端按 7.4 优先级裁决）。

**三类执行标签**

| 执行标签 | 提额 | 降额 | 典型场景 |
| --- | --- | --- | --- |
| 不参与调额 `no_adjust` | ❌ | ❌ | 回捞组、各实验组 |
| 仅参与提额 `increase_only` | ✅ | ❌ | Staff 组、白名单组 |
| 仅参与降额 `decrease_only` | ❌ | ✅ | 风险触发组、人工降额名单组 |
| 未命中 | ✅ | ✅ | 常规用户 |

**记录状态（列表展示与筛选口径，按实际时间派生）**

| 状态 | 条件 |
| --- | --- |
| 生效中 | 在 [生效时间, 失效时间) 内且未停用 |
| 未生效 | 当前时间早于生效时间 |
| 已失效 | 当前时间到达失效时间（到期自动失效，记录保留可查） |
| 已停用 | 手工停用（不删除；停用优先于时间窗展示） |

## 5. 名单维护方式

### 5.1 文件上传（增量合并）

- 上传 Excel/CSV；解析 → 校验 → **整批通过后按同键合并进当前名单**：
  - 同键记录：**以新文件为准整体覆盖**（执行标签 / 明细组 / 生效时间 / 失效时间一并更新；停用状态按"用新的"重置为正常）；
  - 文件中没有的旧记录（**含手工维护**）**全部保留**。
- 上传前展示解析预览：**解析条数 / 新增 / 覆盖 / 非法**。
- **任一行校验不通过 → 本次整批放弃**（不产生任何名单变化，不做部分生效），失败明细列到行号与原因。
- 提供导入模板下载（CSV，列：`third_customer_id / overdraft_id / tag_level / pool_type / detail_group / effective_start / effective_end / remark`）。
- **逐行校验规则**：
  1. `tag_level` 必填且在枚举内；
  2. 用户级：`third_customer_id` 必填，`overdraft_id` **必须为空**；账户级：`overdraft_id` 必填，`third_customer_id` **必须为空**；
  3. `pool_type` 必须在枚举内；
  4. `detail_group` 为空或属于 8 个预设组；
  5. `effective_start` / `effective_end` 必填，格式固定 `YYYY-MM-DD HH:mm:ss`；开始时间不得早于当前时间（opco 本地时间）；失效时间必须晚于生效时间；
  6. 文件内同键重复：按「用新的」处理（后行覆盖前行）。
- 导入通过后：批次进入「处理中」，落库完成后转「已生效」；导入后名单条数 = 原条数 + 新增。

### 5.2 单条新增

- 表单字段：标签层级（用户级 / 账户级）→ **只呈现对应 ID 输入框**（用户级只出 `third_customer_id`、账户级只出 `overdraft_id`，物理上不允许填写对方 ID）；
- 执行标签（三选一）、明细组（8 预设，可不选）、**生效时间与失效时间（必填；开始时间默认当前、不得早于当前）**、备注；
- **同键已存在 → 拦截提示**：*该 ID 已存在一条记录——新增不会覆盖，如需更新请用上传覆盖*；
- 跨层级共存允许（同一人的用户级与账户级记录互不冲突）。

### 5.3 单条删除 / 停用·启用

- **删除**：二次确认后从名单移除；立即不再参与匹配；**不可恢复**；
- **停用（不删除）**：停用后不参与匹配、可随时启用；停用状态在下次同键覆盖导入时重置为正常；
- 两者均作用于「当前名单」，不影响已发生的历史拦截记录。

### 5.4 批次管理

- 批次 = **一次导入的变更记录**；列表：批次号 / 来源 / 条数 / 状态 / 操作人 / 创建时间；操作列**仅「详情」**；
- 状态机：**处理中 →（成功）已生效 / （异常）处理失败**；处理失败的批次不产生任何名单变化，失败原因在详情中展示；
- 详情：批次信息（解析条数、新增 / 覆盖数、操作人、时间）+ 失败原因（如有）+ 本批记录预览；
- 「生效批次」「恢复为生效」等名单版本概念**取消**（增量模型下名单 = 历史导入累积的合并结果）。

### 5.5 名单列表交互

- **展示列**：third_customer_id / overdraft_id / 标签层级 / 执行标签 / 明细组 / 生效时间 / 失效时间 / 状态 / 来源 / 更新时间 / 操作；
- **分页**：显示总条数、每页条数（10 / 20 / 50 / 100）、页码、跳页；名单量级为几十万，分页为必需能力；
- **筛选**（9 项）：third_customer_id、overdraft_id、生效时间（范围）、失效时间（范围）、明细组、标签层级、执行标签、来源、状态；查询 / 重置；筛选后回到第 1 页；
- 分页与筛选由后端分页查询实现（不要把全量名单拉到前端）。

## 6. 生效规则

- **有效期窗口**：记录仅在 [生效时间, 失效时间) 内参与调额匹配；**到期自动失效**（不参与匹配，记录保留、可查询可删除）；
- **停用**：手工停用的记录不参与匹配，与时间窗独立；
- **同键覆盖**：同一 ID 再次导入即用新值更新（含时间窗、标签、明细组）；
- 无冷却期；退出名单 = 删除（立即生效）或 停用 / 到期（窗口结束）。

## 7. 执行时的匹配与拦截

### 7.1 校验位置（关键）

调额执行链路：**DE → LMS → ECW（核心额度系统）**

LMS 逐条调额的现有执行顺序（`QuotaImportProcessServiceImpl.processLimitUpdate`）：

```
① 读明细 → ② 冷却期校验 → ③ 比对目标额度 vs 当前额度 → 确定方向（提额/降额）
        → ④ 计算可用额度 → ⑤ 调用核心 ECW 改额度 → ⑥ 落额度历史与流水
```

**名单校验插入在 ③ 之后、⑤ 之前。** 原因：判断"只提不降 / 只降不提"必须先知道本次方向。

### 7.2 必须覆盖所有调额入口

- 校验放在**共用的执行方法**中，所有调额入口（DE 推批次、人工 Excel 批量导入等）都经过它，一次覆盖全部入口；
- **不允许**只在某一个入口做校验。

### 7.3 为什么不能只在导入批次时校验

**目标额度是导入时确定的，但当前额度是执行那一刻读取的**，中间用户额度可能已变化，方向会变。因此：

- **执行时校验是权威的**（必须做）；
- 导入/生成批次时可做提前预筛（可选，用于减少无谓执行），但不能替代执行时校验。

### 7.4 匹配规则（命中优先级：odid → tcid）

```
按 overdraft_id 匹配账户级记录（且在有效期内、未停用）
    ↓ 命中 → 按其执行标签处理
    ↓ 未命中
按 third_customer_id 匹配用户级记录（且在有效期内、未停用）
    ↓ 命中 → 按其执行标签处理
    ↓ 未命中
走常规逻辑
```

**为什么账户级优先（v1.0 顺序的有意修正）**：账户级池（实验 / 回捞）全部是「不参与调额」——提降都拦的**全锁（最严格）**；用户级池是单向锁（仅提额 / 仅降额）。先账户级命中：

- 实验样本不会被提额 / 降额溜进来（样本纯净）；
- 人本身也得到全锁保护（全锁天然满足任何单向保护）；
- 反之（v1.0 的「先用户级」）会让 Staff 的『仅参与提额』把提额放行到实验账户，污染样本。

该顺序即「**最严格优先**」的落地形态；若未来出现「账户级单向标签」，冲突不可比时需按最严格优先原则重新对齐（见 13）。

**拦截矩阵**（对最终命中的那条记录）

| 命中标签 | 本次方向=提额 | 本次方向=降额 | 处理 |
| --- | --- | --- | --- |
| 不参与调额 | ❌ 拦截 | ❌ 拦截 | 维持当前额度，不调核心 |
| 仅参与提额 | ✅ 放行 | ❌ 拦截 | 降额时维持当前额度 |
| 仅参与降额 | ❌ 拦截 | ✅ 放行 | 提额时维持当前额度 |
| 未命中 | ✅ 放行 | ✅ 放行 | 常规逻辑 |

## 8. 异常与兜底

| 场景 | 处理 |
| --- | --- |
| 名单查询报错 / 超时 | **整批终止**，不做静默放行；记录失败原因并告警，人工介入后重跑 |
| 名单为空 | 视为未命中，全部走常规逻辑（需在下发前确认名单已维护） |
| 用户不在名单 / 记录不在有效期 / 记录已停用 | 走常规逻辑 |
| 导入落库异常 | 批次标记「处理失败」，**不产生任何名单变化**，失败原因可在批次详情查看 |

> 说明：选择"整批终止"是因为漏拦（该拦没拦）会放大风险敞口与实验污染；常规逻辑在名单可用后重跑即可补上。

## 9. 留痕与可追溯

- 被拦截的记录：写入执行明细的处理状态**「跳过」**，并写明**具体原因**：
  - `命中非常规组-不参与调额`
  - `命中非常规组-仅参与提额`
  - `命中非常规组-仅参与降额`
- 禁止只写笼统的「跳过」；
- 每条拦截记录保留：用户/账户标识、本次方向、命中的执行标签、命中的明细组、**命中的层级与命中键（`overdraft_id` 命中 / `third_customer_id` 命中）**、所用名单快照版本；
- **名单快照**：一次调额执行开始时一次性加载名单（快照），执行期间使用同一份内存快照，避免执行途中名单变更导致前后口径不一致；留痕记录快照时间戳（或版本号）；
- 对账口径：风控圈选 N 条 → 实际执行 M 条 → 拦截 N−M 条，可按原因 / 标签 / 明细组 / **命中层级**下钻。

## 10. 性能与容量

- 名单规模预计**几十万条**；
- ❌ 禁止在逐条执行循环中逐条查库；
- ✅ 推荐：批次开始时**一次性加载名单到内存**（或与明细表做 join 合并），循环内做本地匹配；
- 需要研发给出：一次调额批次规模 × 名单规模下的执行耗时评估。

## 11. 关键约束

1. **单 ID 互斥**：用户级行仅 `third_customer_id`、账户级行仅 `overdraft_id`；不允许出现对方层级的 ID；
2. **同键唯一 + 增量覆盖**：同一层级内同 ID 仅一条记录；再次导入 = 用新值覆盖；单条新增同键 → 拦截提示；
3. **跨层级共存 + 命中优先级**：同一人的用户级与账户级记录允许共存；执行端按 `odid → tcid` 顺序命中（账户级优先）；
4. **有效期全必填**：开始时间不得早于当前（opco 本地时间）；到期自动失效；停用不参与匹配；
5. 名单表只存非常规用户，常规用户不入表。

## 12. 验收要点

1. 未命中名单的用户（含记录不在有效期内、已停用），提额/降额均按常规执行，行为与改造前一致；
2. 命中「不参与调额」：不论方向，均标记跳过、原因 `命中非常规组-不参与调额`，且**不调用核心接口**；
3. 命中「仅参与提额」：本次为提额时正常执行；本次为降额时标记跳过、原因 `命中非常规组-仅参与提额`，额度维持不变；
4. 命中「仅参与降额」：本次为降额时正常执行；本次为提额时标记跳过、原因 `命中非常规组-仅参与降额`；
5. **所有调额入口**（DE 推批次、人工批量导入）都触发名单校验；
6. 模拟名单查询异常 → **整批终止**且不产生任何额度变更，有明确错误提示；
7. 上传文件含任一行校验失败（单 ID 互斥违规 / ID 缺失 / 时间格式 / 开始时间早于当前 / 失效早于生效 / 组不在预设）→ **整批放弃**并给出明细；
8. 上传通过 → 同键记录被新值覆盖、其余记录（含手工维护）保留；名单条数 = 原条数 + 新增；批次转「已生效」；
9. 单条新增同键已存在 → 拦截提示；同一人的跨层级记录可共存，不互相拦截；
10. 停用记录不参与匹配、启用后恢复；到期记录自动不参与匹配；
11. **跨层级同时命中**（同一人既有用户级记录、又有当前账户的账户级记录）→ 按 `overdraft_id` 优先执行，拦截原因体现账户级命中；
12. 时间校验：开始时间早于当前（opco 本地时间）被拦截；`effective_end` 必须晚于 `effective_start`；
13. 批次状态机：处理中 → 已生效；处理失败批次不产生名单变化、详情可见失败原因；操作列仅「详情」；
14. 拦截记录可按原因、执行标签、明细组、**命中层级**查询与导出，用于与风控圈选名单对账。
