## 0. 本版变更摘要（v1.0 → v1.1）

1. **单 ID 互斥**：用户级记录只允许携带 `third_customer_id`、账户级记录只允许携带 `overdraft_id`，两列均不允许出现对方层级的 ID；
2. **导入语义**：由「全量覆盖」改为**增量合并**——同键（同层级同 ID）以新文件为准覆盖，其余记录（含手工维护）全部保留；任一行校验不通过 → 本次整批放弃；上传预览改为「解析 / 新增 / 覆盖 / 非法」；
3. **新增有效期**：`effective_start` / `effective_end` 全必填，时间格式固定 `YYYY-MM-DD HH:mm:ss`；开始时间不得早于当前（opco 本地时间）；到期自动失效；
4. **匹配优先级修正**：执行端由「先用户级后账户级」改为 **「先账户级（overdraft_id）后用户级（third_customer_id）」**——账户级池全部是「不参与调额」（全锁、最严格），先命中可同时保证实验样本纯净与用户级保护不被稀释（详见 7.4；此为对 v1.0 的**有意修正**）；
5. **一人一标签放宽**：由「全名单内一人仅一条」改为**「同键唯一 + 跨层级共存」**——同一个人的用户级记录与其各账户的账户级记录可并存，执行端按优先级裁决；
6. **批次模型**：批次由「名单版本」改为**「一次导入的变更记录」**；状态机为 **处理中 / 已处理 / 处理失败**；操作列「详情」（2026-10-16 追加「下载」，见 0.1-9）；「生效批次」「恢复为生效」概念取消；
7. **维护能力**：新增 **单条删除**（不可恢复）与 **停用 / 启用（不删除）**；记录状态派生展示（未生效 / 生效中 / 已失效 / 已停用）；
8. **筛选与命名**：名单筛选扩展为 9 项（third_customer_id、overdraft_id、生效时间范围、失效时间范围、明细组、标签层级、执行标签、来源、状态）；「用户标识 / 账户标识」统一更名为 `third_customer_id` / `overdraft_id`。

> 变更依据：2026-10-15/16 用户调研（14 条需求更正）与评审讨论（增量合并、有效期、odid → tcid 优先级）。

12. （2026-10-19 追加）新增 **`product_code` 业务产品**：**本期固定 `OD`**（单条新增、文件模板、列表、筛选均仅 OD），字段保留以便后续扩展（BL 等）。
13. （2026-10-19 追加）**明确特殊组自身调额口径：不设豁免**——执行侧一律以执行时刻的生效名单为准；如要对名单内对象调额（回捞 / 实验 treatment），由名单维护方**先停用或删除该记录**（或让记录生效时间晚于本次调额），调额执行后再按需重新加入（详见 §7.5）。

## 1. 背景与问题

贷中调额的现有流程是：**DE（风控决策引擎）每月全量跑批 → 风控依据跑批落库结果线下圈选用户 → 形成调额名单文件 → 交大数据执行调额**（落到 LMS → 核心 ECW 实际改额度）。

问题在于，调额策略对所有人一视同仁，但下面这几类人**不能被常规策略碰**：

- **Staff组、白名单组**：不能被降额（降自己人/白名单用户会引发投诉与合规问题），但提额合理；
- **风险触发组、人工降额名单组**：不能被提额（已经因风险被人工压过额度，系统不能自动提回去）；
- **回捞组、激进提额组、降额实验组、模型切换实验组**：在实验期/回捞期内**完全不能被常规策略干扰**，否则组内样本被污染，实验结论不可信。

目前没有机制承载这件事：风控靠人工记着"这批人不要动"，一旦漏记或交接断层，就会误伤。

## 2. 目标与范围

**目标**：建一张"非常规组名单"，并在**每次调额执行前**按名单做门禁，实现三类差异化处理；常规用户不存表、默认走常规逻辑。

**In Scope（v1.1）**

- 名单表与维护后台（增量导入 / 单条新增 / 单条删除 / 停用·启用 / 批次管理）
- 名单有效期（生效 / 失效时间）
- LMS 调额执行前的名单校验（覆盖所有调额入口；命中优先级 odid → tcid）
- 拦截留痕与对账、操作审计

**Out of Scope（v1.1 明确不做）**

- ❌ **冷却期**：不做 cooldown，仅按有效期窗口生效
- ❌ 贷前、催收、短信触达等其他场景的名单复用
- ❌ 同层级内的多记录与更复杂的优先级裁决（本期为「同键唯一 + 固定 odid → tcid 优先级」）
- ❌ 单条编辑（替代流程：上传覆盖，或删除后新增；见 §13）

## 3. 术语与角色

| 术语 | 说明 |
| --- | --- |
| 特殊执行名单 / 非常规组名单 | 同一对象的两个称谓：系统页面名「特殊执行名单」，含义「非常规组名单」——只存需要特殊处理的用户/账户，常规用户不入表 |
| 执行标签 | 决定调额时怎么处理的标签：不参与调额 / 仅参与提额 / 仅参与降额 |
| 标签层级 | `user`（绑客户，跨账户）/ `account`（绑账户）。生命周期：**用户级跟人**——客户换户/重注册后仍应继续命中（依赖 `third_customer_id` 的稳定性）；**账户级跟账户**——仅在其 `overdraft_id` 存在期内命中，新账户不继承（换户后新账户无记录、自然不命中） |
| 单 ID 互斥 | 用户级记录只带 `third_customer_id`、账户级记录只带 `overdraft_id`；不允许出现对方层级的 ID |
| 同键 | 同一层级内相同的 ID（用户级看 `third_customer_id`、账户级看 `overdraft_id`） |
| 增量合并 | 导入时「同键用新值覆盖、其余保留」的合并方式 |
| 批次 | 一次导入的变更记录（**不是**名单版本）；状态：处理中 / 已处理 / 处理失败 |
| 有效期 | 记录在 [生效时间, 失效时间) 内参与调额匹配；到期自动失效 |
| 命中优先级 | 执行端先按 `overdraft_id` 命中账户级；未命中再按 `third_customer_id` 命中用户级 |

| 角色 | 职责 |
| --- | --- |
| 风控 | 圈定名单、确定执行标签 |
| 运营/额度岗 | 在后台维护名单、上传/导入、停用/删除、查看拦截结果 |

## 4. 名单模型

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| third_customer_id | string | 用户级必填 | 用户唯一标识；**用户级记录仅允许携带此 ID**（账户级行必须为空） |
| overdraft_id | string | 账户级必填 | 账户唯一标识；**账户级记录仅允许携带此 ID**（用户级行必须为空）；**仅允许与 `product_code = OD` 同时出现**（非 OD 产品该列必须为空） |
| tag_level | string | 是 | `user` / `account` |
| pool_type | string | 是 | `no_adjust` / `increase_only` / `decrease_only` |
| product_code | string | 是（本期固定 OD） | 业务产品：**本期固定 `OD`**（仅 OD 可选，保留字段以便后续扩展）；后续产品的账户键由实现映射（OD = `overdraft_id`） |
| detail_group | string | 否 | 明细组，8 个预设组之一：回捞组 / 激进提额组 / 降额实验组 / 模型切换实验组 / Staff组 / 白名单组 / 风险触发组 / 人工降额名单组。**仅作归因 / 统计 / 对账维度，不参与匹配与拦截裁决** |
| effective_start | datetime | 是 | 生效时间；不得早于提交时的当前时间（opco 本地时间，判定细则见 §5.1） |
| effective_end | datetime | 是 | 失效时间；必须晚于生效时间；不设上限 |
| source | string | 是 | `file`（文件上传）/ `manual`（手工维护） |
| batch_no | string | 导入记录必填 | 最近一次由文件导入更新该记录时的批次号；纯手工维护记录为空（列表展示「—」） |
| operator | string | 是 | 操作人 |
| remark | string | 否 | 备注 |
| created_at / updated_at | timestamp | 是 | 时间戳 |

**存储约束**

- **单 ID 互斥**：用户级行 `overdraft_id` 必须为空；账户级行 `third_customer_id` 必须为空；
- **同键唯一**：同一业务产品 + 同一层级内同一 ID 仅允许一条记录；再次导入 = 用新值覆盖（增量合并）；单条新增同键已存在 → 拦截提示；
- **跨层级共存**：同一个人的用户级记录与其各账户的账户级记录允许并存（执行端按 §7.4 优先级裁决）。

**同键覆盖的字段更新口径**

| 字段 | 覆盖行为 |
| --- | --- |
| created_at | 保留（首次入库时间不变） |
| updated_at / operator / batch_no / source | 更新为本次导入（source=file） |
| tag_level / pool_type / product_code / detail_group / effective_start / effective_end | 取新值 |
| 停用状态 | 按「用新的」重置为正常 |
| remark | 以新值为准 |

**三类执行标签**

| 执行标签 | 提额 | 降额 | 典型场景 |
| --- | --- | --- | --- |
| 不参与调额 `no_adjust` | ❌ | ❌ | 回捞组、各实验组 |
| 仅参与提额 `increase_only` | ✅ | ❌ | Staff组、白名单组 |
| 仅参与降额 `decrease_only` | ❌ | ✅ | 风险触发组、人工降额名单组 |
| 未命中 | ✅ | ✅ | 常规用户 |

**明细组与层级/标签的对照（风控圈选口径约定）**

| 明细组 | 标签层级 | 执行标签 |
| --- | --- | --- |
| 回捞组 / 激进提额组 / 降额实验组 / 模型切换实验组 | 账户级 | 不参与调额 |
| Staff组 / 白名单组 | 用户级 | 仅参与提额 |
| 风险触发组 / 人工降额名单组 | 用户级 | 仅参与降额 |

> 说明：以上为**组目录**（产品维护的 8 行配置）：单条新增选择明细组后，标签层级与执行标签**自动带出并锁定**（选「不指定」时自由选择）；文件上传时按本目录做**交叉校验**——明细组非空而层级/执行标签不一致 = 非法行（整批失败）；明细组留空时不校验。§7.4 的优先级安全性论证基于「账户级池均为不参与调额」这一约定。

**记录状态（列表展示与筛选口径，按实际时间派生）**

派生优先级：**已停用 > 未生效 > 已失效 > 生效中**（未生效与已失效不会同时成立）；列表展示与状态筛选均按此口径。

| 状态 | 条件 |
| --- | --- |
| 生效中 | 在 [生效时间, 失效时间) 内且未停用 |
| 未生效 | 当前时间早于生效时间（且未停用） |
| 已失效 | 当前时间到达失效时间（且未停用；记录保留可查） |
| 已停用 | 手工停用（不删除；展示优先于时间窗） |

> 状态是派生展示值，不是独立字段：停用是人为开关，已失效是时间到期。一条记录可同时「被停用」+「已过期」，列表按优先级只显示「已停用」；对已过期且停用的记录执行启用 → 仍显示「已失效」，需先修改有效期。两种状态都不参与匹配。

## 5. 名单维护方式

### 5.1 文件上传（增量合并）

- 上传 Excel/CSV；解析 → 校验 → **整批通过后按同键合并进当前名单**：
  - 同键记录：**以新文件为准整体覆盖**（字段更新口径见 §4；停用状态按"用新的"重置为正常）；
  - 文件中没有的旧记录（**含手工维护**）**全部保留**。
- 上传前展示解析预览：**解析条数 / 新增 / 覆盖 / 非法**；预览中需明确提示：**同键覆盖会将已停用记录重置为正常**（原型以固定提示展示）。
- **任一行校验不通过 → 本次整批放弃**（不产生任何名单变化，不做部分生效），失败明细列到行号与原因；**同时生成一条「处理失败」的变更记录**（类型=文件导入、对象数=解析条数、原因=行校验失败，详情可下载失败明细，便于修正后重传），名单零变化。
- 校验失败时：页面展示前若干条失败明细（含总数）；提供「**下载失败明细**」（CSV：行号 + 原数据行 + 失败原因列，可直接修正后重传）。
- 提供导入模板下载（CSV，列：`third_customer_id（用户ID）`、`overdraft_id（账户ID）`、`tag_level（标签层级）`、`pool_type（执行标签）`、`product_code（业务产品）`、`detail_group（明细组）`、`effective_start（生效时间）`、`effective_end（失效时间）`、`remark（备注）`）；解析按字段名（括号前）匹配，**兼容纯英文表头**；模板要求时间列以**文本格式**填写；解析需兼容 Excel 常见变体（日期序列号、区域化格式）并给出明确的非法原因；文件编码 UTF-8（兼容 BOM）；
- **单文件上限 100 万行**（不含表头），超出请拆分上传，选文件后即提示。
- **逐行校验规则**：
  1. **ID 格式**：去除首尾空格后校验；`third_customer_id` 为 64 位十六进制字符串、`overdraft_id` 为纯数字（与生产数据实测口径一致）；格式不合规计入非法行；
  2. `tag_level` 必填且在枚举内；
  3. 用户级：`third_customer_id` 必填，`overdraft_id` **必须为空**；账户级：`overdraft_id` 必填，`third_customer_id` **必须为空**；
  4. `pool_type` 必须在枚举内；
  5. `detail_group` 为空或属于 8 个预设组；
  6. `effective_start` / `effective_end` 必填，格式固定 `YYYY-MM-DD HH:mm:ss`；开始时间不得早于当前时间；失效时间必须晚于生效时间；
  7. 文件内同键重复：按「用新的」处理（后行覆盖前行），明细中提示行号；
  8. **组目录交叉校验**：`detail_group` 非空时，`tag_level` 与 `pool_type` 必须与该组在组目录（§4 对照表）中的定义一致，否则计入非法行；`detail_group` 为空时不校验；
  9. **业务产品**：`product_code` 本期仅允许 `OD`（留空按 `OD` 处理），其他值计入非法行；后续开放其他产品时再扩展枚举；
  10. **产品与账户键绑定**：`overdraft_id` 仅允许在 `product_code = OD` 时出现；`product_code` 非 OD（后续 BL 等）时该列必须为空——各产品账户键独立，BL 的账户键待定义，不得占用 `overdraft_id` 列。
- **时间判定细则**：以服务端接收「确认导入」时刻为基准，按 opco 业务时区（UG：Africa/Kampala，UTC+3）判定；允许不超过 5 分钟的钟差宽限（与原型一致）；等于当前时间的边界允许。
- **计数口径**：解析条数 = 文件数据行数；新增 + 覆盖 + 非法 = 解析条数；文件内同键重复并入「覆盖」。
- 导入通过后：批次进入「处理中」，落库完成后转「已处理」（事务与并发要求见 §5.6）；导入后名单条数 = 原条数 + 新增。

### 5.2 单条新增

- 表单字段：标签层级（用户级 / 账户级）→ **只呈现对应 ID 输入框**（用户级只出 `third_customer_id`、账户级只出 `overdraft_id`，物理上不允许填写对方 ID）；
- 执行标签（三选一）、**业务产品（本期固定 OD，不可修改）**、明细组（8 预设，可不选）、**生效时间与失效时间（必填；开始时间默认当前、不得早于当前）**、备注；
- **明细组级联**：选择明细组后，标签层级与执行标签自动带出并**锁定**（由组目录决定，界面提示「由明细组决定」）；选择「不指定」时两者恢复自由选择；
- 表单字段校验与 §5.1 逐行规则一致（ID 格式、枚举、组范围、组目录交叉校验、时间规则；单 ID 互斥由界面呈现方式保证）；
- **同键已存在 → 拦截提示**：*该 ID 已存在一条记录——新增不会覆盖；如需更新请用上传覆盖，或删除后重新新增*；同键存在性校验**包含已失效 / 已停用记录**（同键唯一是存储约束）；
- 跨层级共存允许（同一人的用户级与账户级记录互不冲突）。

### 5.3 单条删除 / 停用·启用

- **删除**：二次确认后从名单移除；立即不再参与匹配；**不可恢复**；
- **停用（不删除）**：**二次确认**后停用；停用后不参与匹配、可随时启用；停用状态在下次同键覆盖导入时重置为正常；
- **批量操作**：首列勾选支持两种作用域——本页全选、再次点表头变为「全选当前筛选结果」（跨页）；选择后显示「已选择 N 条 / 已选择全部 N 条（当前筛选结果）」与「清除选择」；**勾选 ≥2 条时「批量停用」「批量删除」才可用**（只选 1 条保持置灰，单条用行内操作）；两个批量操作均二次确认，批量删除为**硬删除、不可恢复**（不做审批、不做回收站）；
- **启用细则**：**二次确认**后启用；对已过失效时间的停用记录执行「启用」→ 启用成功但状态仍为「已失效」，页面提示先更新有效期；
- **生效时点**：停用 / 删除对**之后启动**的调额执行生效；执行中的批次以开始时的快照为准（见 §9）；
- 删除 / 停用均作用于「当前名单」，不影响已发生的历史拦截记录。

### 5.4 变更记录（导入批次 + 页面操作）

- **一张表、两类来源**：文件导入与页面操作（批量停用 / 批量删除 / 单条新增 / 删除 / 停用 / 启用）合并为一条流水，用「类型」列区分；
- **一次操作 = 一条记录**（导入按批次、页面操作按次），不按行落日志；列：编号、类型、对象数、状态、操作人、时间、操作；
- **状态**：只有「文件导入」有处理中 →（成功）已处理 /（异常）处理失败；页面操作即时生效，状态显示「已完成」；
- **操作列按类型**：导入行「下载原文件 + 详情」，页面操作行「详情 + 导出清单」（导出受影响对象快照 CSV）；
- **详情**：上半部分操作信息（类型、对象数、操作人、时间、失败原因可选），下半部分对象清单；批量操作的二次确认中显示对象条数；
- 批次的定义不变：**一次导入的变更记录**；处理失败批次不产生名单变化，失败原因在详情展示；保留原文件供下载（含失败批次），保留期限按合规要求；
- 行校验失败的上传生成一条**处理失败**的导入记录（含失败明细下载），名单零变化；单条 / 批量操作**即时生效**；
- 「生效批次」「恢复为生效」等名单版本概念**取消**（当前名单 = 历次导入合并结果 + 手工维护净影响）。

> 失败信息展示口径：批次级失败原因在页面（列表 + 详情）展示；行级校验失败以「页面概要（前若干条 + 总数）+ 可下载的失败明细文件」呈现。

### 5.5 名单列表交互

- **展示列**：勾选列 / third_customer_id / overdraft_id / 标签层级 / 执行标签 / 业务产品 / 明细组 / 生效时间 / 失效时间 / 状态 / 来源 / 更新时间 / 操作；
- **分页**：显示总条数、每页条数（10 / 20 / 50 / 100）、页码、跳页；名单量级为几十万，分页为必需能力；
- **筛选**（10 项）：third_customer_id、overdraft_id、生效时间（范围）、失效时间（范围）、明细组、标签层级、执行标签、业务产品（仅 OD）、来源、状态；查询 / 重置位于筛选区右下；筛选后回到第 1 页；
- **列设置**：表头列可勾选显隐（勾选列与操作列固定），默认全显；设置作用于当前浏览器会话（原型），真实系统可持久化到用户偏好；
- 分页与筛选由后端分页查询实现（不要把全量名单拉到前端）。

### 5.6 导入事务与并发（新增）

- **原子性**：一次导入的合并要么全部成功、要么零变化，不产生「半批」状态；
- **处理中不可见**：批次处于「处理中」期间，其变更对执行端**不可见**；合并提交后原子生效；
- **并发**：同一时刻仅允许一个「处理中」批次；上传时如已有处理中批次，提示稍后重试；
- **重试与幂等**：处理失败的批次可安全重跑（重跑产生新批次记录）；重复上传同一文件按新批次处理（不做文件级去重）；
- **超时处置**：处理中超过阈值（建议 10 分钟）告警，由研发提供人工处置手段（重试 / 放弃）；
- **落库异常** → 批次「处理失败」，名单零变化（§8）。

### 5.7 权限与操作审计（新增）

- **权限**：沿用现有后台权限模型（具体角色权限矩阵由研发落地时确认）；
- **操作审计（必需）**：所有影响名单的操作（导入 / 单条新增 / 删除 / 停用 / 启用）写**操作日志**：操作人、时间、对象（用户/账户标识）、字段前后值、来源批次（如有），可查询导出；导入路径通过「批次 + 操作日志」双重留痕；页面入口见 §5.4「变更记录」；
- **高风险操作建议**：Staff组 / 白名单组等保护型记录的删除 / 停用同样二次确认（不做审批流程），并纳入对账可见范围；
- 原型说明：原型不含权限与操作日志模拟。

## 6. 生效规则

- **有效期窗口**：记录仅在 [生效时间, 失效时间) 内参与调额匹配；**到期自动失效**（不参与匹配，记录保留、可查询可删除）；
- **停用**：手工停用的记录不参与匹配，与时间窗独立；
- **同键覆盖**：同一 ID 再次导入即用新值更新（含时间窗、标签、明细组）；
- **到期治理口径**：本期不做到期提醒 / 续期流程（有效期由名单维护方自行管理）；"即将到期"视图如需另议（见 §13）；
- 无冷却期；退出名单 = 删除（立即生效）或 停用 / 到期（窗口结束）。

## 7. 执行时的匹配与拦截

### 7.1 校验位置（关键）

调额执行链路：**DE → LMS → ECW（核心额度系统）**

LMS 逐条调额的现有执行顺序（`QuotaImportProcessServiceImpl.processLimitUpdate`）：

```
① 读明细 → ② 冷却期校验 → ③ 比对目标额度 vs 当前额度 → 确定方向（提额/降额）
        → ④ 计算可用额度 → ⑤ 调用核心 ECW 改额度 → ⑥ 落额度历史与流水
```

**名单校验插入在 ③ 之后、④ 之前；命中拦截即短路，不执行 ④（计算可用额度）与 ⑤（核心调用）。** 原因：判断"只提不降 / 只降不提"必须先知道本次方向；拦截时无需计算可用额度。

### 7.2 必须覆盖所有调额入口

- 校验放在**共用的执行方法**中，所有调额入口（DE 推批次、人工 Excel 批量导入……）都经过它，一次覆盖全部入口；
- **不允许**只在某一个入口做校验；回捞 / 实验 treatment 同样走此共用方法，执行前按 §7.5 先停用 / 删除名单记录；
- **入口清单**：具体入口清单（含是否存在单笔调整等入口）评审时由研发逐项勾对确认；后续**新增入口必须接入共用方法**（纳入变更评审清单）；
- **监控建议**：执行侧监控「本批执行条数 vs 名单校验调用次数」差值，防止入口绕过。

### 7.3 为什么不能只在导入批次时校验

**目标额度是导入时确定的，但当前额度是执行那一刻读取的**，中间用户额度可能已变化，方向会变。因此：

- **执行时校验是权威的**（必须做）；
- 导入/生成批次时可做提前预筛（可选，用于减少无谓执行），但不能替代执行时校验。

### 7.4 匹配规则（命中优先级：odid → tcid）

```
按 overdraft_id 匹配账户级记录（且在有效期内、未停用）
    ↓ 命中 → 按其执行标签处理
    ↓ 未命中
按 third_customer_id 匹配用户级记录（且在有效期内、未停用）
    ↓ 命中 → 按其执行标签处理
    ↓ 未命中
走常规逻辑
```

**作用域（product_code）**：账户级与用户级均按「当前调额产品 + 对应键」匹配；本期业务产品固定 `OD`，实际只命中 OD 类调额（后续扩展产品时按 `product_code` 区分）。

**命中语义与生命周期**：

- **用户级 = 对「人」的约束**：挂在 `third_customer_id` 上——客户换户 / 重注册后仍应继续命中（依赖该 ID 的稳定性）；这正是 Staff/风险类保护必须用用户级的原因；
- **账户级 = 对「账户样本」的约束**：仅在其 `overdraft_id` 存在期内命中，新账户不继承（换户后新账户无记录、自然不命中）；这是实验/回捞的表达方式。

**为什么账户级优先（v1.0 顺序的有意修正）**：账户级池（实验 / 回捞）全部是「不参与调额」——提降都拦的**全锁（最严格）**；用户级池是单向锁（仅提额 / 仅降额）。先账户级命中：

- 实验样本不会被提额 / 降额溜进来（样本纯净）；
- 人本身也得到全锁保护（全锁天然满足任何单向保护）；
- 反之（v1.0 的「先用户级」）会让 Staff 的『仅参与提额』把提额放行到实验账户，污染样本。

该顺序即「**最严格优先**」的落地形态；若未来出现「账户级单向标签」，冲突不可比时需按最严格优先原则重新对齐（见 §13）。

**产品范围**：账户级仅对绑定的产品账户生效（本期 OD 类）；用户级跨产品生效——若其他产品的调额走同一执行方法将被顺带覆盖（需与风控确认口径，见 §13）。

**取数要求**：用户级匹配所需的 `third_customer_id` 必须随调额明细或名单快照**一次性带出**（禁止在执行循环内逐条反查客户主档）。

**拦截矩阵**（对最终命中的那条记录）

| 命中标签 | 本次方向=提额 | 本次方向=降额 | 处理 |
| --- | --- | --- | --- |
| 不参与调额 | ❌ 拦截 | ❌ 拦截 | 维持当前额度，不调核心 |
| 仅参与提额 | ✅ 放行 | ❌ 拦截 | 降额时维持当前额度 |
| 仅参与降额 | ❌ 拦截 | ✅ 放行 | 提额时维持当前额度 |
| 未命中 | ✅ 放行 | ✅ 放行 | 常规逻辑 |

### 7.5 特殊组自身调额的口径（已确认：不设豁免）

**结论**：执行侧**不做任何豁免**，一切以执行时刻的**生效名单**为准。命中「不参与调额」即跳过本次调额（提、降都拦），无论这批人属于哪个组、调额由谁发起。

**对回捞 / 实验 treatment 的要求**：如需要对名单内对象调额，由名单维护方**先把该记录停用或删除**（或让记录的 `effective_start` 晚于本次调额），调额执行后再按需重新加入并设置生效时间。即「先下名单 → 再调额 → 需要时再上名单」，名单生效期与组内调额窗口互斥。

**理由**：名单是唯一的执行口径；任何「带标记跳过校验」的口径都会引入绕行空间（谁能发、怎么防滥用、怎么留痕都要额外定义）。用停用 / 删除 + 有效期表达，规则单一、可审计。

**验收**：见 §12-22（名单内提额被拦）、§12-23（停用 / 删除后正常执行、重新加入后再次被拦）。

## 8. 异常与兜底

| 场景 | 处理 |
| --- | --- |
| 名单查询报错 / 超时 | **整批终止**，不做静默放行；记录失败原因并告警，人工介入后重跑 |
| 名单为空 | 视为未命中，全部走常规逻辑（需在下发前确认名单已维护） |
| 用户不在名单 / 记录不在有效期 / 记录已停用 | 走常规逻辑 |
| 导入落库异常 | 批次标记「处理失败」，**不产生任何名单变化**，失败原因可在批次详情查看 |

> 说明：选择"整批终止"是因为漏拦（该拦没拦）会放大风险敞口与实验污染；常规逻辑在名单可用后重跑即可补上。

## 9. 留痕与可追溯

- 被拦截的记录：写入执行明细的处理状态**「跳过」**，并写明**具体原因**：
  - `命中非常规组-不参与调额`
  - `命中非常规组-仅参与提额`
  - `命中非常规组-仅参与降额`
- 禁止只写笼统的「跳过」；
- 每条拦截记录保留（均为**命中时刻的快照拷贝值**，与名单表后续变更解耦）：用户/账户标识、本次方向、命中的执行标签、命中的明细组、**命中的层级与命中键（`overdraft_id` 命中 / `third_customer_id` 命中）**、所用名单快照（加载时间戳）；留痕保留期限由研发按合规要求确定；
- **名单快照**：一次调额执行开始时一次性加载名单（快照），执行期间使用同一份内存快照；快照以**加载时间戳**标识（如需更强标识，可附记录数 / 内容摘要，由研发定）；停用 / 删除等变更对之后启动的执行生效；
- **对账口径**：风控圈选 N 条 → 实际执行 M 条 → 拦截 N−M 条，可按原因 / 标签 / 明细组 / **命中层级**下钻。口径说明：
  1. 对账单位为**调额执行明细条数**；
  2. 圈选文件中处于未生效 / 已失效 / 已停用的记录不产生拦截，需**单独归类**，避免拦截率虚低；
  3. 因链路 ②（冷却期校验）被跳过的记录单独归类（原因=冷却期），不计入名单拦截 N−M。

## 10. 性能与容量

- 名单规模预计**几十万条**（后期）；单文件上限 **100 万行**；
- ❌ 禁止在逐条执行循环中逐条查库；
- ✅ 推荐：**一次调额执行**开始时一次性加载名单到内存（或与明细表做 join 合并），循环内做本地匹配；
- 用户级匹配所需 `third_customer_id` 的取数耗时（随明细/快照一次带出）纳入评估；
- 需要研发给出：一次调额执行规模 × 名单规模下的耗时评估。

## 11. 关键约束

1. **单 ID 互斥**：用户级行仅 `third_customer_id`、账户级行仅 `overdraft_id`；不允许出现对方层级的 ID；
2. **同键唯一 + 增量覆盖**：同一业务产品 + 同一层级内同 ID 仅一条记录；再次导入 = 用新值覆盖；单条新增同键 → 拦截提示；
3. **跨层级共存 + 命中优先级**：同一人的用户级与账户级记录允许共存；执行端按 `odid → tcid` 顺序命中（账户级优先）；
4. **有效期全必填**：开始时间不得早于当前（opco 本地时间）；到期自动失效；停用不参与匹配；
5. **导入原子性**：校验不过整批放弃；处理中不可见、提交后原子生效；
6. 名单表只存非常规用户，常规用户不入表。

## 12. 验收要点

1. 未命中名单的用户（含记录不在有效期内、已停用），提额/降额均按常规执行，行为与改造前一致；
2. 命中「不参与调额」：不论方向，均标记跳过、原因 `命中非常规组-不参与调额`，且**不调用核心接口**；
3. 命中「仅参与提额」：本次为提额时正常执行；本次为降额时标记跳过、原因 `命中非常规组-仅参与提额`，额度维持不变；
4. 命中「仅参与降额」：本次为降额时正常执行；本次为提额时标记跳过、原因 `命中非常规组-仅参与降额`；
5. **所有调额入口**（DE 推批次、人工批量导入等）都触发名单校验；
6. 模拟名单查询异常 → **整批终止**且不产生任何额度变更，有明确错误提示；
7. 上传文件含任一行校验失败（单 ID 互斥违规 / ID 缺失 / **ID 格式不合规** / 时间格式 / 开始时间早于当前 / 失效早于生效 / 组不在预设 / **组与标签不匹配**）→ **整批放弃**并给出明细，且生成一条**处理失败**的导入记录（可下载失败明细）；
8. 上传通过 → 同键记录被新值覆盖、其余记录（含手工维护）保留；名单条数 = 原条数 + 新增；批次转「已处理」；
9. **文件内同键重复 → 后行覆盖前行**（以最后一行为准），导入成功；
10. **同键覆盖会将已停用记录重置为正常**；
11. 单条新增同键已存在（含已失效 / 已停用记录）→ 拦截提示；同一人的跨层级记录可共存，不互相拦截；
12. 停用记录不参与匹配、启用后恢复；**对已过失效时间的停用记录启用 → 仍为已失效并提示**；到期记录自动不参与匹配；
13. **跨层级同时命中**（同一人既有用户级记录、又有当前账户的账户级记录）→ 按 `overdraft_id` 优先执行，拦截原因体现账户级命中；
14. 时间校验：开始时间早于当前（opco 本地时间，5 分钟宽限口径）被拦截；`effective_end` 必须晚于 `effective_start`；
15. 批次状态机：处理中 → 已处理；处理失败批次不产生名单变化、详情可见失败原因；操作列「下载 + 详情」；
16. **导入处理中期间名单未发生部分变更（原子性）**；
17. 拦截记录可按原因、执行标签、明细组、**命中层级**查询与导出，用于与风控圈选名单对账；
18. 操作审计：导入 / 新增 / 删除 / 停用 / 启用均可在操作日志中查询到操作人、时间与前后值；
19. 文件下载：批次列表 / 详情可下载原文件（含处理失败批次）；上传校验失败可下载失败明细文件（行号 + 原行 + 失败原因列），与页面明细一致；
20. 组目录级联：单条新增选择明细组后，层级 / 执行标签自动带出并锁定；上传文件含「明细组与层级/执行标签不匹配」的行 → 整批失败；
21. 业务产品：本期仅 OD（单条新增固定 OD；上传文件 `product_code` 非 OD 计入非法行）；列表可按业务产品筛选。
22. 「以生效名单为准」：名单内「不参与调额」的对象发起提额 → 被跳过，原因记为 `命中非常规组-不参与调额`（不因所属组或发起方而豁免）；
23. 组内调额：先将该记录停用 / 删除（或把生效时间调到本次调额之后）→ 同一对象的提额正常执行；重新加入名单后再次被拦；
24. 批量操作：勾选 / 全选当前页 → 批量停用、批量删除均二次确认；批量删除后名单条数减少对应条数；
25. 变更记录：导入与页面操作同表展示（类型区分），导入状态为处理中 / 已处理 / 处理失败、页面操作为已完成；一次操作一条记录，对象数正确；详情可查看并导出对象清单。
26. 列设置：勾选 / 取消列名即隐藏 / 显示对应列；勾选列与操作列始终显示；「恢复默认」恢复全部列；
27. 跨页全选：表头连点两次选中当前筛选结果全部 N 条，横幅显示「已选择全部 N 条（当前筛选结果）」，清除选择后横幅消失；批量删除按该作用域执行；
28. 产品与账户键绑定：`product_code` 非 OD 而填写 `overdraft_id` 的行 → 非法行（账户级仅 OD 使用 `overdraft_id`）。
